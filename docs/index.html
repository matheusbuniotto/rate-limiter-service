01

Token Bucket

Pergunta: "tenho tokens disponíveis?" — saldo em tempo real, burst permitido.

Mecanismo Principal
capacity Máximo de tokens no bucket. capacity=10 → no máximo 10 simultâneos.
refill_rate Tokens adicionados por segundo. 1/s → bucket cheio em 10s.
is_allowed() Chama _refill() → verifica tokens ≥ 1 → consome 1 se permitido.
slot vazio Espaço ainda não recarregado. tokens=0 → REJEITA.

⚠ 10 requests instantâneos

Ocioso 10s → _refill() calcula 10s × 1/s = 10 tokens → bucket cheio → 10 requests em milissegundos. Todos permitidos. Isso é burst.

Trade-offs

▶ Vantagens

  • Simples — só um contador + timestamp
  • Permite bursts controlados (feature intencional)
  • capacity e refill_rate independentes
  • O(1) por request — sem histórico

▷ Limitações

  • "Exatamente 10/min" não é garantido
  • Burst pode sobrecarregar serviços downstream
  • Não distingue picos legítimos de ataques
  • Estado distribuído exige Redis ou coordenação

02

Sliding Window Log

Pergunta: "quantas requests nas últimas X segundos?" — histórico preciso, sem burst oculto.

Mecanismo Principal
previous_requests Lista de timestamps. Cada is_allowed() filtra os mais velhos que a janela.
window_seconds Tamanho da janela deslizante. window_seconds=60 → últimos 60s.
capacity Limite de requests na janela. Se len(requests) ≥ capacity → REJEITA.
expirado Timestamps fora da janela são descartados no próximo is_allowed().
Loop de decisão — 3 passos:

1. Filtra: previous_requests = [t for t in previous_requests if now - t < window_seconds]
2. Conta: if len(previous_requests) < capacity
3. Decide: adiciona now e retorna True, ou retorna False

Memória cresce com o tráfego. Ao contrário do Token Bucket que guarda só 2 números, o Sliding Window Log guarda um timestamp por request na janela. Em alta escala (capacity=1000, window=3600s), cada usuário pode ocupar até 1000 entradas em memória. Considere Redis com TTL ou Sorted Sets para produção.
Trade-offs

▶ Vantagens

  • Precisão exata — sem burst oculto
  • Janela realmente deslizante, não fixa
  • Fácil de auditar — o log é o estado
  • Sem estado global entre usuários

▷ Limitações

  • Memória O(n) por usuário ativo
  • Filtragem a cada request (custo linear)
  • Não permite burst — pode ser muito rígido
  • Estado distribuído ainda exige Redis

Comparação

Quando usar cada algoritmo — modelo mental e trade-offs lado a lado.

Critério Token Bucket Sliding Window Log
Modelo mental Saldo de tokens Histórico de timestamps
Memória por usuário O(1) — 2 números O(n) — 1 por request na janela
Burst permitido? Sim — bucket acumula Não — janela é estrita
Precisão da janela Aproximada (rate média) Exata (cada request contado)
Custo por request O(1) O(n) filtragem da lista
Uso ideal APIs com tráfego bursty legítimo Limites rígidos, compliance, billing
Parâmetros capacity + refill_rate capacity + window_seconds
Interface Python TokenBucketStore.is_allowed(id) SlidingWindowStore.is_allowed(id)
Regra prática: se você pode explicar com "máximo N requests por intervalo" de forma exata → Sliding Window. Se precisar de burst controlado ou O(1) garantido → Token Bucket. Para a maioria das APIs públicas: Token Bucket. Para billing e compliance: Sliding Window.
